# ArcheOS 开发路线图

## 文档职责

本文件只定义 ArcheOS 的阶段演化顺序，不承担单个开发任务的实现规格。

- `AGENTS.md`：定义 Agent 的工作规则与权威关系。
- 本 `ROADMAP.md`：定义长期阶段顺序。
- GitHub Issue：定义当前一次开发必须交付什么。
- Durable Spec：仅在某个稳定契约需要被多个 Issue 复用时建立。
- Implementation Plan：由 Codex 在读取 Issue 和现有代码后生成，说明具体如何实现。

当前阶段的实现权威是 GitHub Issue #4。

---

## M0 — 治理与基础结构（已完成）

目标：建立最小且统一的系统治理方式。

交付：

- `AGENTS.md` 治理规则；
- 信息生命周期目录；
- 系统文档目录；
- `Issue → Plan → 实现 → 测试 → PR → 审核` 的协作协议。

---

## M1 — 通用音频信息消化（当前）

目标：证明 ArcheOS 能把一段未知业务领域的音频，从混乱输入转化为可人工审核的信息包。

第一版输入：

- 会议录音；
- 通话录音；
- 工作讨论；
- 头脑风暴；
- 其他本地音频。

核心流程：

**录音 → 转写 → 上下文保留 → 原子信息候选 + 残渣 → 人工审核**

其中：

- `transcript` 保存原始转写；
- `meeting_summary` 保存整体上下文，不被原子化替代；
- `atomic_notes` 保存可独立审查、可追溯的信息候选；
- `residue` 保存当前无法安全吸收的信息，并作为信息消化健康度的反馈；
- 未解决问题属于会议上下文或原子信息，不建立独立 `questions` 产物。

M1 的边界：

- 不自动更新 `Person`、`Company`、`Project` 等核心对象；
- 不做销售、品牌、项目等领域专用分析；
- 不建立数据库、知识图谱或 UI；
- 停止在人工审核边界。

当前实现：GitHub Issue #4 — `Implement the M1 universal information processing pipeline`。

---

## M2 — 人工确认与对象吸收

目标：让经过人工确认的信息，从“候选信息”安全进入长期结构化对象。

核心问题：

- 哪些 atomic notes 可以被确认；
- 如何修改、拒绝或保留不确定信息；
- 如何识别同一个人物、公司、项目或事件；
- 多次来源的信息如何合并，而不是简单覆盖；
- 如何保留每次更新的来源和历史。

第一阶段优先支持：

- `Note`
- `Person`
- `Company`
- `Project`
- `Event`

M2 完成后，一位客户多次到店、一个项目多次会议等信息，才能逐步聚合到同一个长期对象中。

具体吸收契约必须在进入 M2 前由架构决策明确，并拆成对应 Issue。

---

## M3 — Domain Agent（领域解释）

目标：在通用信息消化能力之上增加业务领域的专门理解，而不污染 ArcheOS Core。

候选领域：

- Sales Agent：客户需求、担忧、决策信号、销售表现、下一步跟进；
- Brand Agent：品牌定位、目标客户、价值主张、差异化、待验证假设；
- Project Agent：项目状态、风险、阻塞、下一步行动。

原则：

- Domain Agent 使用 Core 已产生的上下文、原子信息和结构化对象；
- Domain Agent 可以生成领域报告或提出对象更新建议；
- 不为每一种录音重新实现一套独立的信息处理 Pipeline；
- 领域概念不自动升级为新的 Core 对象类型。

---

## M4 — 决策与反馈闭环

目标：让结构化信息真正参与决策，并通过行动结果反过来更新系统。

核心链路：

**Goal → Decision → Action → Feedback**

需要解决：

- 目标如何表达；
- 哪些信息支持或反对某项判断；
- 决策如何记录依据；
- 行动结果如何反馈到对象、知识和后续决策。

`Goal`、`Decision` 的具体模型在进入 M4 前再收敛，不提前扩大 ontology。

---

## M5 — 多格式输入

目标：在通用信息消化链已经通过真实音频验证后，把相同 Core Pipeline 扩展到更多输入格式。

候选输入：

- PDF；
- 图片；
- PPT；
- 视频；
- 其他文档与外部信息源。

原则：新增输入格式只扩展“如何进入 Processing”，不复制新的对象体系、决策体系或生命周期。

---

## 演化总原则

ArcheOS 始终沿一条主线演化：

**Input → Processing → Atomic Information → Structured Object → Decision → Feedback**

会议纪要、残渣、领域报告等都是这条主线中的辅助产物或解释能力，不建立平行生命周期。

先用真实数据验证当前阶段，再进入下一阶段；不因为未来可能需要某个能力，就提前建设完整框架。
